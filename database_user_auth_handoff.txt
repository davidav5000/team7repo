TEAM 7 CAMPUS ACTIVITIES WEB APP
DATABASE HANDOFF: USER / AUTHENTICATION CONTRACT

PURPOSE
You are working on the PostgreSQL database layer for the Team 7 Campus Activities web app.
Another developer is implementing user accounts, login, logout, sessions, validation, and security on the Node.js + Express backend.

Your task is to make the PostgreSQL user schema compatible with the authentication code without overwriting or redesigning unrelated work.

IMPORTANT WORKFLOW
1. Inspect the current repository and your current database branch before changing anything.
2. Preserve any existing database work that is already correct.
3. Do not modify authentication/controller code unless a schema conflict makes it unavoidable.
4. If your existing schema uses different names or incompatible data types, report the mismatch before renaming/removing existing fields.
5. Use PostgreSQL and the project's existing `pg` connection layer.
6. Use migrations/schema SQL that can be reviewed and committed to the repository.
7. Do not store credentials, passwords, or secrets in source control.

CURRENT BACKEND DATABASE INTERFACE
The Node.js application already uses:

    models/db.js

with:

    db.query(sql, params)

All application queries use PostgreSQL parameter placeholders such as:

    $1, $2, $3

Do not replace the shared database connection layer unless required by the team.

REQUIRED USER TABLE CONTRACT

The authentication code currently expects a table named:

    users

Required columns:

    id
    name
    username
    contact_info
    password_hash

Required behavior:

- `id` is the primary key.
- `name` is required.
- `username` is required and UNIQUE.
- `contact_info` is required.
- `password_hash` is required.
- There must NOT be a plaintext password column used for authentication.
- Password hashing is performed by the Node.js authentication layer with bcrypt before INSERT.
- Usernames are normalized to lowercase by the authentication layer before lookup or insertion.
- `contact_info` is intentionally generic. Do not force it to be email-only unless the team explicitly changes that requirement.

RECOMMENDED POSTGRESQL DEFINITION

Use this as the preferred contract unless your current schema already has an equivalent implementation:

    CREATE TABLE IF NOT EXISTS users (
        id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
        name VARCHAR(100) NOT NULL,
        username VARCHAR(32) NOT NULL UNIQUE,
        contact_info VARCHAR(255) NOT NULL,
        password_hash VARCHAR(255) NOT NULL,
        created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
    );

`created_at` is optional from the authentication code's perspective, but is recommended.

AUTHENTICATION QUERIES CURRENTLY EXPECTED

Lookup by username:

    SELECT id, name, username, contact_info, password_hash
    FROM users
    WHERE username = $1
    LIMIT 1;

Create user:

    INSERT INTO users (
        name,
        username,
        contact_info,
        password_hash
    )
    VALUES ($1, $2, $3, $4)
    RETURNING id, name, username, contact_info;

Lookup current user's public profile:

    SELECT id, name, username, contact_info
    FROM users
    WHERE id = $1
    LIMIT 1;

The authentication layer intentionally does not return `password_hash` in public user responses.

UNIQUE USERNAME REQUIREMENT

The database MUST enforce uniqueness for `username`.

This is required even though the Node.js application checks for an existing username before INSERT.

Reason:
Two registration requests can pass an application-level existence check at almost the same time. The PostgreSQL UNIQUE constraint is the final protection against duplicate usernames.

The authentication controller handles PostgreSQL error code:

    23505

as a duplicate username / conflict response.

PASSWORD SECURITY CONTRACT

The database receives only:

    password_hash

The database must never require or store the user's plaintext password.

Do NOT:
- add a plaintext `password` field for normal authentication,
- hash the password again in PostgreSQL,
- attempt to decrypt password hashes,
- log password values.

The Node.js layer uses bcrypt and sends the completed hash to PostgreSQL.

EXPECTED RELATED TABLE RELATIONSHIPS

Other parts of the application will eventually reference `users.id`.

Likely relationships include:

    activities.creator_id  -> users.id
    comments.author_id     -> users.id
    attendance.user_id     -> users.id

Coordinate the user ID type with those tables. If you use INTEGER for `users.id`, related foreign-key columns should also use INTEGER.

Do not create or rename these related columns solely from this handoff if another teammate already owns those tables. Coordinate rather than overwrite.

SESSION STORAGE

The Express application uses:

    express-session
    connect-pg-simple

Production/development sessions are stored in PostgreSQL.

The application is configured to let `connect-pg-simple` create/manage its session table. Do not create a competing custom authentication-session schema unless there is a specific team decision to do so.

ACCEPTANCE CRITERIA

Database work is compatible with authentication when all of the following are true:

[ ] A `users` table exists.
[ ] `users.id` is a primary key.
[ ] `users.name` is present and required.
[ ] `users.username` is present, required, and UNIQUE.
[ ] `users.contact_info` is present and required.
[ ] `users.password_hash` is present and required.
[ ] No plaintext user password is stored.
[ ] The three authentication queries above execute successfully.
[ ] Duplicate usernames are rejected by PostgreSQL.
[ ] The user ID type is compatible with future activity/comment/attendance foreign keys.
[ ] Existing unrelated database work has not been overwritten.
[ ] Schema/migration changes are committed on the database feature branch and ready for review.

INTEGRATION NOTE

The authentication work currently lives on the feature branch:

    user-auth

    POST /register

Therefore `users.id` must remain a stable unique identifier.
